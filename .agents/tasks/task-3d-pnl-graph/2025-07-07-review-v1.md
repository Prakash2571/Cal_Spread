# 3D PnL graph with orbit controls for calendar spread trades

A new `PnlGraph3D` component renders PnL versus time and open interest as a 3D line in a Three.js scene. The user can rotate, pan, and zoom the graph via OrbitControls. It appears inside the existing `StockDetail` view whenever a trade is loaded and OI history is available. The integration passes the full `Trade` object from `App.tsx` through `StockDetail` and into the new component.

**Watch for:** The zero-plane is oriented incorrectly — it renders perpendicular to the Y-axis instead of the Z-axis (PnL), so it doesn't visually represent the "break-even" level (confirmed). The PnL calculation silently produces wrong results when `trade.closed_at` exists and history extends beyond the close date, because it keeps using current closes instead of capping at the trade's exit prices (confirmed). Rendering individual `<mesh>` elements per data point will cause React reconciliation overhead that scales linearly with history length — tolerable for ~30 daily points but problematic if the history source ever returns larger datasets (likely).

## High-level view

The component uses `@react-three/fiber` and `@react-three/drei` to render a single polyline colored green/red by PnL sign, with small spheres at each data point. Orbit controls provide the interactive rotation the user asked for. The scene includes axis labels, a grid helper on the floor, and a semi-transparent "zero plane" meant to indicate break-even.

PnL is computed per-date by replaying the trade's entry against daily closing prices for both legs. The calculation assumes the trade is always open (uses live closes), which is correct for open trades but overstates the graph for closed trades that have fixed exit prices. The component filters dates `>= openDate` but has no upper bound, so for closed trades the graph extends beyond the close date with phantom PnL movements.

<summary>Issues (4)</summary>

1. **Zero-plane orientation** — The break-even plane is rotated around X by π/2 and positioned along the Z-axis, but Z is PnL in scene coordinates. The rotation makes it face the Y direction (OI) instead of lying flat across the PnL dimension. Rotate it to `[0, 0, 0]` and position at `z = normalize(0, zRange[0], zRange[1])`, or adjust to match whichever scene axis actually carries PnL.
2. **PnL overshoot for closed trades** — When `trade.status === "closed"`, the graph should cap at `trade.closed_at` or use `trade.buy_close`/`trade.sell_close` for dates after exit. Currently it uses live closes indefinitely.
3. **Axis mapping inconsistency** — The mapping puts `timeIndex → X`, `oi → Y`, `pnl → Z` in the tuple, while Three.js treats Y as "up". PnL visually reads as depth rather than height, which is confusing since height is the natural axis for magnitude. Consider swapping OI and PnL so PnL is the vertical axis.
4. **Per-point mesh elements** — Each data point creates a separate React element with its own `<sphereGeometry>`. For the current ~30-point daily dataset this works, but if history grows (or an intraday mode is added), this pattern will stall rendering. An `InstancedMesh` would handle scale better.

## PnL calculation produces phantom movements for closed trades

The core PnL formula:

```typescript
const pnl =
  trade.lot_size *
  ((buyPoint.close - trade.buy.entry) + (trade.sell.entry - sellPoint.close));
```

For closed trades, `trade.buy_close` and `trade.sell_close` hold the actual exit prices. The graph should either stop at `trade.closed_at` or, if it shows post-close data for context, switch to using the exit prices after that date. Without this, a closed trade that booked +5000 PnL could show it drifting to -2000 on the graph because the futures kept moving after exit. (confirmed)

## Zero-plane faces the wrong direction

The plane is constructed at:

```typescript
<mesh
  position={[0, 0, normalize(0, zRange[0], zRange[1])]}
  rotation={[Math.PI / 2, 0, 0]}
>
  <planeGeometry args={[scaleSize * 2, scaleSize * 2]} />
```

A `planeGeometry` lies in the XY plane by default (faces +Z). Rotating by π/2 around X makes it lie in the XZ plane (faces +Y). Since PnL is the Z-axis in the data mapping, the plane should face the Z direction to slice through it at zero — meaning it should stay unrotated in XY, positioned at `z = normalize(0, ...)`. The current rotation makes it horizontal (floor-like) at the correct depth but facing the wrong way: it visually marks a zero-OI level instead of zero-PnL. (confirmed)

## Axis semantics vs. Three.js conventions

Three.js convention is Y-up. The component maps PnL to the Z tuple position, which means PnL extends along the depth axis. This makes the most important variable the hardest to read visually, since humans intuit height as magnitude. The camera position at `[8, 6, 8]` gives a 45° view that partially compensates, but swapping the mapping so PnL occupies the Y position (height) and OI occupies Z (depth) would align visual intuition with the data and make the zero-plane orientation simpler. (likely — consistent with standard 3D chart conventions)
